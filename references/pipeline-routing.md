# 按画质要求选择导出路径

目标是在本次交付要求内，采用项目实际支持且已验证的较快路径。这个技能指导检查、选择和接入；它不会把任意剪辑工程自动转换为另一套渲染器。

## 先确定交付要求

沿用用户明确要求和工程已有输出配置，记录以下会影响结果的项目：

- 原素材、时间线范围、分辨率、帧率、时长，以及全部字幕、字体、布局、图层、转场和音频编辑。
- 视频编码、容器、目标播放器／发布平台；是否要求透明度、HDR、10位、特定色彩空间或色调映射。
- 画质优先级与体积限制：目标码率、允许的**实际视频码率范围**，或参考画面与可接受的质量差异。

“高清”不能只靠分辨率或码率一个数字判定。未约定码率时，先保留已有质量设置；需要改变交付质量、编码格式或兼容范围时，再说明取舍。不要把某次实验的6.4Mbps或某个误差百分比变成所有项目的默认值。

同实际码率比较观察该数据预算下的速度与画质；同画质比较观察达到质量目标所需的码率、大小与时间。两者不能互相代替。码率设置值相同，也不保证实际码率相同。

## 运行环境检查

WebCodecs是浏览器内置接口。只有选择该路径时，才需要在实际导出进程中确认安全上下文、`VideoEncoder`／`VideoFrame`及实际使用的解码接口；Node.js存在或系统安装了浏览器不能代替这一步。网页部署通常使用HTTPS；符合条件的localhost可用于本地开发。[接口](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API)、[安全上下文](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts)

使用本次完整视频配置调用`VideoEncoder.isConfigSupported()`，按需检查解码和音频配置。检测通过只说明配置支持，不证明本次实际用了硬件，也不证明字幕合成与MP4输出已接好。[配置检测](https://developer.mozilla.org/en-US/docs/Web/API/VideoEncoder/isConfigSupported_static)

检查工程是否已有取帧→组件合成→编码→音轨／封装的完整实现与配套依赖。首次补齐后验证代表片段并保存配置，后续复用有效结果；不每次重装环境。缺少WebCodecs时选择现有可用路线，仍可减少等待、中间转换与重复封装；不将浏览器接口支持缺口当作自动降质的理由。

## 路径选择

| 当前工程能力 | 优先尝试 | 保真回退 |
|---|---|---|
| 原渲染器已能直接提供最终画面帧 | 保留原组件合成，减少中间图片转换，直接送入可用编码器 | 原有已验证导出入口 |
| Remotion工程已满足Web Renderer支持范围 | 使用其公开API与当前版本配套的依赖，先验证代表镜头 | 保留原Remotion渲染路径；不要删效果来让快路径通过 |
| HTML／HyperFrames适配器仍大量截图与逐帧往返 | 在适配器支持时减少PNG编码、跨进程回传和重复像素转换 | 保留完整DOM捕获，或只对经证明可组合的部分使用快路径 |
| 已有完整MP4，仅需封装或音轨变更 | 能复制的视频流不重新编码；按本次编辑生成或复制音轨 | 只有确需画面变更、格式转换时才重编码 |
| 路径不支持用户要求的效果、色彩或输出格式 | 保持原保真路径，报告具体限制 | 不静默降分辨率、帧率、位深或删字幕图层 |

Remotion浏览器端渲染使用WebCodecs与Mediabunny，但只支持部分标签和CSS。一个工程可用，不等于所有React组件、滤镜、布局或转场都可直接迁移。[官方说明](https://www.remotion.dev/docs/web-renderer)

“部分走快路径”也需要合成设计：确认图层顺序、遮罩、混合、字体、转场和时间戳能正确重组；不能把同一帧分开渲染后简单叠加就假定等价。适配成本高于本次任务收益时，使用已有可靠路径。

## 缩短画面准备与交接

1. **取正确的帧。**优先使用适配器支持的直接解码取帧，保留裁剪、变速和源时间戳规则。不能靠跳帧、重复帧或放松选帧条件加速。
2. **保留原合成语义。**让解码画面进入最终合成所需的组件／画布；检查字幕、图形、布局、转场与颜色后，再减少中间bitmap、canvas和格式转换。不要宣称零拷贝，除非已测得。
3. **以就绪事件推动流水线。**用带帧身份的ready通知替换无必要的固定等待；源帧和组件确实就绪后才提交。避免把“减少等待”改成“忽略尚未完成的绘制”。
4. **有界并行与背压。**在供帧、合成、编码与写入之间设置有界队列，根据内存和编码器队列控制节奏。正确释放VideoFrame／bitmap；先定位等待位置，再决定是否增加线程。

PNG可以只在内存管道中传递，仍需压缩、传输和解压。移除PNG落盘与移除PNG转换是不同改动；原素材生成留下的帧序列也不能算作每次最终导出的新增占用。

## 编码与音轨封装

- 使用当前浏览器／系统实际支持的编码配置。WebCodecs的`prefer-hardware`只是偏好，能力检测通过也不等于已实际启用硬编；保存运行时编码器证据，取不到证据时明确“硬件启用未证实”。[WebCodecs规范](https://www.w3.org/TR/webcodecs/#hardware-acceleration)
- 检查当前FFmpeg可用编码器；FFmpeg也可以调用平台硬件编码。不要把“FFmpeg／WebCodecs”直接等同于“软件／硬件”。[FFmpeg文档](https://ffmpeg.org/ffmpeg.html)
- 兼容交付通常先保留项目的H.264方案；用户需要H.265的体积或格式特性时，再检测编码、封装与目标端播放。不因编号更大就认为更快；已有H.265实测也不能外推到另一设备或参数。
- 音频有变更时，按本次口播、配乐、音量、剪辑及淡入淡出生成新音轨。只在音频内容和时间线均未变、缓存身份有效时复用已验证音轨。
- 在能力允许时，将本次视频码流与本次音轨直接封装为最终MP4，减少无声MP4中间件和外层二次读写。一次封装不要求使用旧音轨；复制已编码包也不会自动完成混音。FFmpeg的stream copy不重新编码被复制的流。[封装与转码区别](https://ffmpeg.org/ffmpeg.html#Streamcopy)

## 在本次任务内验证与收口

先复用同条件、仍有效的验证记录。路线、素材类型、效果或质量要求改变时，选能覆盖变化的短样本检查；普通导出不要无条件展开全套测速矩阵。

- 确认实际编码、尺寸、帧率、帧数／时间戳、时长、音轨、真实视频packet码率与最终文件可解码。
- 对比细字、暗部、运动、渐变、转场、复杂图层与色彩；像素或客观指标必须说明参考和测量范围，不能自动等同主观清晰度。
- 区分文件检查、解码检查、目标浏览器局部播放、完整人工观看／听取和用户验收。
- 比速度时固定输入、质量约定、计时边界和存储条件；总时钟包含本次要求的音轨处理与最终封装。浏览器API、同步提交成本和flush等待都不是孤立的硬件编码耗时。
- 按现有资源限制设置队列和临时输出位置，保留工程与历史产物。未获授权不清理旧文件；通过相关验证后完成本次导出，不继续自动扩展参数实验。

若要让项目的固定导出命令必经这些检查，应将选择与验证接入该项目实际导出入口。技能的隐式匹配本身不是所有编辑器导出按钮的运行时拦截器。
